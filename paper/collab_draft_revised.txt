Story/thesis:
Existing multi-agent KG construction systems (KARMA, CooperKGC, OneKE) treat the knowledge graph as a flat output artifact which agents extract, a controller merges, and the pipeline terminates. The resulting graph has no organizational memory: no record of which agent produced which fact, no domain structure governing updates, and no mechanism for routing queries to the knowledge owners. We argue that a knowledge graph should not be a passive store but a governed memory partitioned into domain-owned subgraphs where every triple is admitted through an explicit governance decision, every decision is auditable, and downstream applications like QA route through domain experts rather than flat retrieval.

What is, in one sentence, the takeaway for this whole system- We propose the Governed Knowledge Graph, a data structure in which every triple is admitted through an explicit ownership-and-review protocol, and show that governance shapes graph structure and enables principled downstream reasoning.

Why this methodology or architecture is necessary
Agents vs. other approaches?-
1. Specialization reduces error modes. Entity extraction, relation extraction, and evidence verification have different failure modes. Specializing agents lets you diagnose and fix each independently.
2. Conflict resolution requires arbitration. When two agents disagree on a triple, you need structured deliberation, not a single model's confidence score. Multi-agent voting produces a decision with a rationale.
3. Domain ownership requires distributed expertise. A single model has no principled reason to route a triple about methodology to a "methods" domain. Domain expert agents instantiate the ownership function φ. A single LLM baseline can't do any of these.

Domain-expertise for data modularity - Each domain d ∈ D is a coherent subgraph- a region of the graph with a common conceptual scope, a set of owning entities, and a relation schema. The ownership function φ partitions the graph into these regions. This enables: (a) modular updates- only the owning domain validates a proposed new triple; (b) modular queries- downstream applications route to the relevant expert rather than doing flat retrieval; (c) modular auditing- every decision is traceable to a specific domain owner.

Governed Knowledge Graph
Definition 1.
 A Governed Knowledge Graph is a tuple (G = (E, T, D, φ, γ)), where:
E is a set of entities.
 T ⊆ E × R × E is a set of typed triples.
 D = {d₁, …, d_k} is a set of domains.
 φ: E → 2^D is an ownership function assigning each entity to one or more governing domains.
 γ: T → {approve, reject, revise, escalate, auto_approve} is a governance function over proposed triples.

This definition differs from a standard knowledge graph in two ways.
First, the graph contains an explicit organizational layer through domains and ownership.
Second, admission into the triple set is mediated through governance rather than direct insertion.
In implementation, this is realized through a two-phase protocol: propose a triple, obtain a governance decision, and then commit that decision. This changes the graph from a passive fact store into a managed memory structure.

The ownership function is written as φ: E → 2^D, rather than φ: E → D, because one entity may legitimately belong to more than one domain. In a scientific corpus, the same entity can participate in multiple conceptual regions of the graph: a method may belong to a methods domain and also sit inside a task-specific domain; a biomarker may belong to both an inflammation domain and a cardiometabolic domain. Using 2^D means φ(e) returns a set of owners, not a single owner. This is what makes cross-domain governance possible. Once entities have domain assignments, a triple can be classified as single-owner, cross-domain, or unowned depending on the ownership of its endpoints.

Operationally, the data structure consists of more than entities and triples. A governed triple also carries an ownership assignment, a governance action, a rationale, and an audit record. In the implementation, every admitted triple passes through propose_triple(...), produces a GovernanceDecision, and is then committed through commit_decision(...). This is the concrete mechanism that instantiates γ. The graph therefore stores not only what is known, but also how that knowledge entered memory and who was responsible for it.

The main research idea is therefore not multi-agent extraction in isolation, but knowledge creation and proliferation under domain-governed memory.

System Overview
The system has three layers.
The first is the creation layer, which turns documents into entities and triples.
 The second is the governance layer, which organizes knowledge into domains and controls admission into memory.
 The third is the application layer, which uses the governed graph for downstream tasks such as question answering and incremental enrichment.
The contribution of the paper lives in the first two layers. The third layer demonstrates usefulness but is not the center of the claim.

One additional point is important for understanding the real system behavior: the graph is built cumulatively over a corpus, not rebuilt from scratch for each document. After document 1 is processed, accepted entities and triples become part of the shared governed memory. Document 2 is then processed against that already-populated memory, and so on. This means the system is not simply extracting isolated document-level KGs. It is constructing one accumulating governed KG whose entity inventory, domain structure, aliases, and audit log grow over time.

The implementation also supports multiple governance regimes. In audit_only mode, every triple is routed and logged but automatically admitted after routing. In permissive mode, ownership routing is still recorded but review is lightweight. In strict mode, the governance board can actively approve, reject, revise, or escalate a proposal. This matters for the experiments: the large creation runs mainly demonstrate routing, ownership, and auditability, while the separate strict-governance benchmark demonstrates selective review quality.

Knowledge Graph Creation Workflow
The system receives a corpus of documents. A top-level orchestrator agent manages the end-to-end creation process over the full corpus and over each document instance.
The pipeline is mostly sequential. Each specialized agent transforms or validates the current representation and passes it to the next stage. This is intentionally simple. The system only activates deliberation when an agent signals uncertainty or conflict.

The workflow is as follows.
The DocumentProcessor segments each document into coherent chunks.
The DomainClassifier derives a working schema for the document. In benchmark mode it uses a fixed schema; in open-world mode it discovers entity and relation types from the content. From this schema, the system bootstraps preliminary domains before any triples are admitted. This is the first point at which governance becomes active during creation.
The EntityExtractor identifies entity mentions, canonical labels, and candidate types. The shortest-meaningful-noun-phrase rule is used only to normalize the entity span itself, so that entities are anchored to compact canonical labels rather than overly long surface forms. Relation extraction is not limited to noun pairs: downstream agents still use the full sentence context, including predicates, modifiers, and supporting evidence, to determine whether a typed relation should be proposed between the extracted entities. The extractor is also instructed to preserve short scientific terms, abbreviations, tool names, and task phrases rather than discarding them as generic text.
Once entities exist, they are assigned to one or more domains. This partially instantiates the ownership function (φ), allowing the system to know who owns a proposed fact during creation.
The RelationExtractor identifies relations between current entities and produces candidate triples. In fixed-schema benchmark mode, the extractor is constrained to the benchmark label set; in open-world mode, it can propose a new relation structure.
The EvidenceLinker attaches supporting text spans and source references to each candidate triple.
The VerificationAgent removes unsupported or low-quality extractions and outputs a verified set of triples suitable for admission review.
At that point, the KnowledgeOrganizer and governance layer take over. Each verified triple is proposed to the governed graph rather than inserted directly. The system routes the triple to the relevant domain or domains, produces a governance decision, commits the decision, and appends that decision to the audit log.
This is the step that distinguishes governed creation from ordinary extraction.

There are several important operational details that the workflow above relies on:

1. The corpus is processed incrementally. After each document, newly accepted entities and triples are committed to the shared KG. Later documents therefore see a richer memory than earlier documents.
2. Entity resolution happens against both the current document and the pre-existing graph. A new mention is compared to entities already extracted in the current document, entities already present in the KG, and aliases stored in shared memory. This allows later documents to attach to canonical entities created earlier in the corpus.
3. Domain bootstrapping happens before triple admission, but domain ownership becomes sharper as more entities are assigned and the graph grows. Early domains are preliminary ownership shells; later they become coherent subgraphs with actual members and cross-domain edges.
4. Governance happens after extraction-time deliberation, not instead of it. Deliberation asks whether an uncertain extraction should survive. Governance asks how a surviving triple should enter memory.

What happens when a new document arrives can therefore be described precisely. The system does not create a separate mini-KG and merge it blindly. It segments the document, derives a schema, extracts entities, resolves those entities against the existing graph and alias store, assigns them to one or more domains, extracts candidate triples, attaches evidence, filters low-quality proposals, and only then proposes each surviving triple to the governed memory. The routing step uses the ownership assignments of the subject and object to determine whether the triple is single-owner, cross-domain, or effectively unowned. The governance regime then determines whether the triple is automatically accepted after routing, or whether it must be actively reviewed by the responsible domain expert(s).

The post-routing cases should be stated explicitly:
- Single-owner triple: both endpoints resolve to the same governing domain, so that domain becomes the primary owner.
- Cross-domain triple: the endpoints belong to different domains, so the triple is treated as shared knowledge between owners.
- Unowned triple: no stable owner can be derived from the current org chart, so the triple is escalated or logged accordingly.

The governance action itself can be one of five outcomes:
- approve: accept the triple as-is
- reject: do not admit it to memory
- revise: admit a normalized or corrected version of the triple
- escalate: mark it for explicit review because ownership or evidence is insufficient
- auto_approve: admit it automatically under a lightweight governance regime while still recording the event

Deliberation, Blackboard, and Voting
The pipeline is sequential by default. Deliberation is an exceptional path triggered when an agent reports low confidence. In the current implementation, a threshold around 0.7 is used as the key decision boundary.
If an agent’s confidence is above threshold, the pipeline continues.
 If confidence falls below threshold, the agent raises a hypothesis.
A hypothesis is a structured claim about an extraction unit that is not trusted enough for automatic continuation. Typical hypothesis types are an uncertain entity, an uncertain triple, or an uncertain relation type.
Each hypothesis includes the proposed content, the posting agent, the initial confidence, the supporting evidence, and the current pipeline context.
The blackboard is a shared forum inside the shared memory system. It is not a chat interface; it is a structured coordination object.
An agent posts a hypothesis to the blackboard, and the deliberation coordinator asks a set of evaluator agents to vote on it.
Each voter is not necessarily a topical expert, but an expert on a criterion.
The EntityExtractor evaluates whether the entity hypothesis is plausible.
The RelationExtractor evaluates whether the relation structure is coherent.
The EvidenceLinker evaluates whether the text supports the proposal.
This means the value of a vote comes from specialized perspective, not topical ownership. Deliberation here is about extraction reliability.
Domain governance happens later, when the triple enters the governed KG.
Each voting agent returns a vote with rationale. The coordinator aggregates the votes and resolves the hypothesis into a keep or no-keep decision. If votes conflict, the coordinator can trigger a short structured debate.
The final decision and rationale are written back to shared memory, creating an audit trail.

This distinction between deliberation and governance is central and should be explicit in the paper. Deliberation is an extraction-time reliability mechanism. It is triggered by uncertainty in an intermediate hypothesis. Governance is a memory-admission mechanism. It is triggered when a triple is proposed to the governed KG. The blackboard helps decide whether a questionable extraction should survive the pipeline. The governance protocol decides how an extracted fact enters long-term memory and which domain owner is accountable for that admission.

Example. During extraction of the sentence "Amorph identifies proper nouns and NE items in Japanese text," the EntityExtractor proposes the entity "Amorph" with type Method and confidence 0.48- below the 0.7 deliberation threshold. It posts a hypothesis to the blackboard: {type: "entity", content: "Amorph", label: "Method", confidence: 0.48, evidence: "appears as subject of verb 'identifies'"} The deliberation coordinator asks three agents to vote. The EntityExtractor votes Accept (0.75): "Short noun in subject position is consistent with a tool name." The RelationExtractor votes Accept (0.80): "The entity participates as subject of a typed action, consistent with Method." The EvidenceLinker votes Strong Accept (0.90): "Explicit agent-action pattern in source text." Weighted consensus: 0.82 > threshold. The hypothesis is accepted and written to semantic memory. The pipeline continues. Had the RelationExtractor voted Reject ("no semantic consistency with known method types"), the coordinator would have triggered a one-round debate. If still unresolved, the entity would have been discarded.

Shared Memory
The shared memory system has two roles.
First, it supports extraction-time coordination. The blackboard, pending hypotheses, vote rationales, and local task state all live here.
Second, it supports corpus-scale consistency. The memory stores canonical entities, aliases, prior extractions, and procedural patterns.
Conceptually, the memory system has four regions:
Episodic memory for per-document processing history.
 Working memory for current pipeline state.
 Semantic memory for accepted graph structure and alias mappings.
 Procedural memory for learned extraction and organization heuristics.

The alias and canonicalization functionality is especially important for corpus-scale operation. When a later document mentions an entity already seen earlier, the system can resolve that mention to the existing canonical node rather than creating an unnecessary duplicate. This is one of the main ways the system turns multiple document-level extractions into one accumulating governed memory.

Output Schema
The output of the creation pipeline is a JSON serialization of the governed graph.
At minimum, it contains the knowledge graph, the org chart, the governance mode, and the audit log.
Each entity stores an ID, labels, a type, and metadata (such as source document and confidence).
Each triple stores a subject, relation, object, confidence, source, and metadata.
The org chart is the organizational view of the graph. Each domain includes:
A domain identifier
A label and description
Seed entity and relation types
Current entity membership
A domain-specific subgraph
Cross-domain relations
The org chart summary is a compressed textual view listing domain names, descriptions, relation signatures, and entity coverage.

The audit log should also be described concretely. Each governance record stores the proposed triple, the assigned owner domain(s), the governance action, a rationale, a timestamp, and whether the decision was eventually committed. If a triple is revised, the revised triple is also stored. This makes the auditability claim operational rather than rhetorical: the graph can be inspected not only as a set of facts, but as a history of how those facts were admitted.

Applications Built on Top of the Governed KG
The governed KG is the core object, and applications sit on top of it.
One application is question answering. A QA orchestrator reads the org chart summary, routes a question to domain experts, collects subgraph-grounded answers, and synthesizes a final response.
Another application is incremental enrichment. New documents are processed, candidate triples are extracted, compared to the base graph, and reviewed under the same governance protocol before being added.

The enrichment path is worth stating more explicitly because it is the true "new information arrives" setting. The system first runs extraction on the new documents into a temporary delta KG. It then computes a diff between the delta KG and the base KG, identifying new entities, new triples, and conflicts with existing triples. New triples are sent to the governing owner domains for review. Conflicting triples are resolved either by the governance board or by a fallback conflict resolver. Only accepted changes are merged back into the base KG. In this sense, enrichment is not a second unrelated system: it is the additive counterpart to the initial governed creation pipeline.

Experimental Setup
We evaluate MaKG along four empirical axes.

First, we evaluate KG construction quality on the SciERC test split in fixed-schema mode. SciERC provides gold entity spans, entity types, and typed relations over scientific abstracts. In this setting, the extraction schema is fixed to the SciERC label set so that all systems are evaluated against the same target ontology. This gives hard benchmark metrics: entity F1, strict triple F1, fuzzy/mapped triple F1, and triple hallucination. Strict triple F1 requires exact agreement on subject, relation, and object. Fuzzy/mapped triple F1 is more forgiving about surface normalization and relation-label canonicalization; this is important because many apparent errors are canonicalization mismatches rather than genuinely unsupported facts.

Second, we run governance ablations over the same 50-document GPT-5 candidate proposal stream. These ablations ask whether MaKG is better because of governance itself or merely because some other part of the pipeline filters triples. The ablations remove different pieces of the governance stack: source filtering only, deterministic domain rules, a centralized global reviewer, and finally full domain-memory governance.

Third, we prepare a human triple review study. This is necessary because SciERC is a closed benchmark annotation, not an exhaustive list of every valid scientific fact in an abstract. A triple can be supported by the source text and useful for the graph while still being counted as a false positive under SciERC if it is absent from the gold annotation. The human review study samples governed-only, flat-only, shared, and revised triples and asks annotators to judge support, relation correctness, endpoint correctness, graph usefulness, and governance decision quality.

Fourth, we evaluate downstream QA on MuSiQue, a multi-hop QA dataset. MuSiQue is useful here because it tests whether the graph can support chaining across documents rather than only retrieving one local sentence. We run a 50-question MuSiQue slice with supporting-only contexts and compare MaKG domain-routed QA against graph-based baselines, especially official Microsoft GraphRAG. This tests whether the governed graph can be used as a stronger QA substrate than a standard graph-based retrieval system.

Results
The completed results support four claims.

1. Governance improves the admitted graph relative to flat insertion.
2. The improvement is not explained by source filtering or deterministic domain rules alone.
3. Domain experts become strongest when they carry domain-local memory.
4. The governed graph is useful for downstream QA relative to another graph-based system.

1. KG Construction Quality

The first result compares direct flat KG insertion against two governed variants of MaKG on the same 50 SciERC test documents using GPT-5. All three systems share the same extractor, model, fixed SciERC schema, and document set. The only difference is how candidate triples are admitted into the stored graph.

The Flat KG baseline directly inserts extracted triples into a single global graph. It has no ownership layer, no governance decision, no revision step, and no domain-local memory.

MaKG basic governance routes each candidate triple to the owning domain and applies governed admission before commit. The reviewer sees the candidate triple, its source evidence, the ownership assignment derived from the subject and object, and the endpoint neighborhood in the current graph. The reviewer can approve, reject, or revise the triple. This tests whether governance already improves graph quality even before adding richer domain memory.

MaKG domain-memory governance is the full system. It keeps the same governed routing and evidence-based admission, but the domain expert also carries local memory: previously accepted and rejected relation patterns, recent revised examples, endpoint membership in the owning domain, and nearby admitted triples in the domain subgraph. This is the strongest version of the claim in the paper, because it turns governance from a generic review step into a domain-owned memory process.

Table 1 — GPT-5 KG construction quality on 50 SciERC test documents

| System | Entities | Triples | Strict Triple F1 | Fuzzy/Mapped Triple F1 | Triple Hallucination | TP / FP / FN |
|---|---:|---:|---:|---:|---:|---:|
| GPT-5 Flat KG | 703 | 1366 | 0.116 | 0.204 | 92.7% | 100 / 1266 / 251 |
| GPT-5 MaKG basic governance | 687 | 750 | 0.144 | 0.305 | 89.5% | 79 / 671 / 272 |
| GPT-5 MaKG domain-memory governance | 687 | 472 | 0.173 | 0.333 | 85.0% | 71 / 401 / 280 |

The flat KG has the highest raw triple count, but most of those triples do not match the SciERC gold graph. It produces 1366 triples, of which 1266 are counted as false positives under strict SciERC matching. MaKG basic governance is substantially more selective: it reduces the admitted graph to 750 triples, improves strict triple F1 from 0.116 to 0.144, improves fuzzy/mapped triple F1 from 0.204 to 0.305, and reduces hallucination from 92.7% to 89.5%. This already shows that governance changes what enters memory rather than acting as a cosmetic layer on top of the same graph.

The full domain-memory version is stronger again. It admits 472 triples, improves strict triple F1 to 0.173, improves fuzzy/mapped triple F1 to 0.333, and lowers hallucination to 85.0%. In other words, adding domain-local memory on top of governed routing gives another clear lift over basic governance. This is the key result for the paper: governance is most effective when domains are not only routing destinations but active memory-holding experts.

The absolute hallucination rates are still high because SciERC is a strict closed-label benchmark and does not treat all source-supported extracted facts as true positives. For that reason, the paper should not claim that extraction is solved. The right claim is narrower and stronger: given the same scientific extraction setting, governed admission produces a cleaner admitted graph than flat insertion, and domain-memory governance is the strongest admission policy tested. Basic governance is worth keeping in the table because it makes the mechanism legible: routing plus review already helps, and routing plus domain-local memory helps more.

2. Governance Ablation

The second result asks what part of governance matters. All rows replay the same 50-document GPT-5 candidate proposal stream from the MaKG audit log, so differences come from admission policy rather than from different extraction outputs.

Table 2 — Governance ablation on 50 SciERC test documents

| Condition | What is removed / kept | Triples | Strict F1 | Fuzzy/Mapped F1 | Hallucination | TP / FP / FN |
|---|---|---:|---:|---:|---:|---:|
| Flat KG | no governance | 1366 | 0.116 | 0.204 | 92.7% | 100 / 1266 / 251 |
| Domain rules only | ownership routing, no LLM reviewer | 978 | 0.131 | 0.262 | 91.1% | 87 / 891 / 264 |
| Global reviewer, minimal | centralized approve/reject reviewer, no domain memory | 674 | 0.146 | 0.304 | 88.9% | 75 / 599 / 276 |
| Global reviewer, matched | centralized reviewer with stronger matched rubric | 533 | 0.167 | 0.330 | 86.1% | 74 / 459 / 277 |
| MaKG domain-memory reviewer | domain routing + local domain memory + endpoint neighborhood | 472 | 0.173 | 0.333 | 85.0% | 71 / 401 / 280 |

This ablation is the cleanest evidence that governance matters. Domain rules alone help but remain below MaKG, showing that ownership without review is insufficient. A minimal centralized global reviewer is competitive with basic MaKG, which is expected because both are performing isolated triple filtering. However, the full MaKG domain-memory reviewer is the strongest row: it exceeds both the minimal and matched global reviewer on strict F1 and fuzzy/mapped F1 and has the lowest hallucination.

The important interpretation is not that every domain label magically improves extraction. The result is that domain expertise becomes useful when it is implemented as memory. The domain-memory reviewer does not merely see a candidate triple and evidence. It also sees the owning domain, endpoint membership, local accepted/rejected relation patterns, and nearby admitted triples. This gives the reviewer information that a single global reviewer does not have. This is exactly the mechanism the paper argues for: the KG is a governed organizational memory, not a flat list of triples passed through a generic judge.

We also run a smaller source-filtering ablation to check whether the MaKG gain is merely caused by EvidenceLinker and VerificationAgent filtering unsupported triples before insertion. This ablation is run on a 10-document slice because it invokes the full evidence-linking and verification path.

Table 3 — Evidence-only ablation on 10 SciERC test documents

| Condition | Triples | Strict F1 | Fuzzy/Mapped F1 | Hallucination | TP / FP / FN |
|---|---:|---:|---:|---:|---:|
| Flat KG | 305 | 0.163 | 0.265 | 89.5% | 32 / 273 / 56 |
| EvidenceLinker + Verification only | 298 | 0.124 | 0.228 | 91.9% | 24 / 274 / 64 |
| MaKG basic governance | 166 | 0.165 | 0.362 | 87.3% | 21 / 145 / 67 |

Evidence-only filtering does not explain the MaKG result. On the 10-document slice, source filtering plus verification underperforms MaKG on strict F1, fuzzy/mapped F1, and hallucination. This supports the claim that the governance layer changes admission behavior beyond simply requiring evidence text.

3. Human Triple Review

The automatic SciERC evaluation is useful but incomplete. It penalizes any predicted triple absent from the gold annotations, even if the source text supports it. To address this, we create a human review sample from the 50-document GPT-5 construction experiment.

Table 4 — Human triple review sample design

| Group | Source | Purpose |
|---|---|---|
| Governed-only triples | admitted by MaKG, absent from flat KG | checks whether governance adds supported useful facts |
| Flat-only triples | admitted by flat KG, absent from MaKG | checks whether governance removes unsupported or noisy facts |
| Shared triples | admitted by both systems | control group for robust facts |
| Revised triples | revised by MaKG before admission | checks whether revision corrects subject/relation/object errors |

The annotation file is `evaluation/results/governance_ablation_samples_gpt5_50docs_with_context.csv`. Each row contains the triple, entity labels, relation, confidence, extracted evidence, full source context, governance rationale when available, and blank annotation columns for support, relation correctness, endpoint correctness, graph usefulness, decision quality, and notes. The `source_context` column is included so annotators can judge the full document evidence rather than a shortened evidence snippet. This human review is important because it tests whether MaKG's alleged false positives are genuinely unsupported or merely missing from the SciERC gold graph.

The expected reporting format after annotation is: support rate for governed-only triples, rejection quality for flat-only triples, robustness of shared triples, and correction quality for revised triples. This study directly validates the governance mechanism in a way that closed benchmark F1 cannot.

4. Downstream QA on MuSiQue

The downstream QA experiment evaluates whether the governed graph is useful for multi-hop question answering. We use a 50-question MuSiQue 2-hop slice. The supporting-only corpus contains 100 contexts across 99 unique titles. We compare MaKG domain-routed QA against official Microsoft GraphRAG, a graph-based retrieval baseline. This is the cleanest downstream comparison for the paper because it asks whether our governed graph structure leads to better graph-based QA than an existing graph-based system.

Table 5 — MuSiQue QA, 50-question slice

| System | Setting | EM | Token F1 | Answer Rate | Interpretation |
|---|---|---:|---:|---:|---|
| GPT-5 GraphRAG | supporting-only | 0.580 | 0.709 | 1.00 | official graph-aware baseline |
| GPT-5 MaKG domain QA | supporting-only | 0.660 | 0.775 | 1.00 | governed graph with domain-routed QA |

MaKG domain QA outperforms official GraphRAG on both exact match and token F1: 0.660 EM versus 0.580, and 0.775 token F1 versus 0.709. This supports the application-layer claim of the paper: the governed graph is not only a storage artifact, but can also be used by downstream applications through domain-routed experts. GraphRAG builds and retrieves from a graph-based representation, but it does not preserve ownership, domain-local memory, or governed routing. MaKG uses the organization of the graph directly during QA, routing questions through domain-owned subgraphs and synthesizing answers from domain expert responses.

Main Takeaway

The final empirical story should be stated as follows. Flat insertion produces a larger graph, but it admits many noisy triples. MaKG improves the admitted graph by adding governance, and the best result appears when domain experts carry local memory rather than acting as generic reviewers. The ablation shows that source filtering alone, deterministic ownership alone, and a centralized global reviewer do not fully explain the result. The full domain-memory governance condition is the strongest construction system tested: it has the best strict F1, best fuzzy/mapped F1, and lowest hallucination. Downstream, MaKG outperforms GraphRAG on MuSiQue graph-based QA, showing that the governed graph can serve as a useful application substrate rather than only a passive storage artifact. The human review study is the final validation layer, designed to show whether triples counted as false positives by SciERC are in fact source-supported and useful for the governed graph.
